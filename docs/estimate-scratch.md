### 1.1 保守工数の評価基準

サマリの「大／中／小」は、あとから仕様変更や不具合対応をするとき、自前の実装をどれだけ抱えるかを相対的に見た目安です（人数×日数の見積ではありません）。

| 方式 | 評価 | 基準 |
| --- | :---: | --- |
| 曼荼羅：スクラッチ | 大 | グラフを一から自前で作っている。あとからの変更も自前修正が中心になり、一部の担当者に負荷が偏りやすい |
| 曼荼羅：Cytoscape.js／GoJS | 中 | ノードや線の描画はライブラリに任せられるが、楕円への配置などは自前。見た目の調整、画面の操作、表示文言も自社で直す必要がある |
| 流出入差：AG Charts | 小 | グラフ製品の標準設定が中心で、独自のグラフ描画の自前実装を持たない |

**結論:** Cytoscape.js／GoJS は表の機能をすべて満たし、**方式間で機能面の差別化はない**。スクラッチはズームのみ非対応だが、カテゴリ間の行き来をグラフで示すこととしては 3 方式とも実装可能である。したがって選定は機能差ではなく、**コスト・開発／保守・サポート**（§3）で行う。

制限事項:

- 線上の件数が重なった場合、数字はずらせない。画面上はツールチップで確認可能。
- PNG ダウンロード／コピーした画像ではツールチップを表示できないため、重なり箇所の件数確認は不可。

#### 実装工数差の根拠（スクラッチ 32 ↔ ライブラリ 22）

上表のとおり、総計差は **−10人日** である（Cytoscape.js／GoJS 同値）。

- **差の本体:** グラフ描画と画像出力（graph + png、10 → 0）。ライブラリ側は、自前のグラフ描画が不要になる  
- **補助処理(helpers) −2:** 線のつなぎ方などの計算はライブラリに任せられるが、ノードに出す名称・数値や、マウスオーバー時の説明（ツールチップ）の用意は自前実装が残る。0にはならない  
- **見た目設定(styles) +2:** ライブラリではスクラッチのグラフ描画(graph)は不要。その代わり、色・形・線の太さなどの見た目指定が増える  
- **api / data / page は同額:** データの取得や画面の操作（表示最小値の操作、画像出力ボタンなど）は、どの方式でも同じように必要なため、工数は減らない  

まとめると、ライブラリを使ってもデータ取得や画面操作などの共通作業は残る。初期の作り込みは 32人日と 22人日で、差は限定的である。選定では初期工数だけでなく、保守のしやすさ（§1.1）とライセンスもあわせて見る必要があり、その観点ではライブラリが有利である。
